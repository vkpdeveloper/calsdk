Time zones are where calendar code goes wrong quietly: a weekly meeting stored as 08:00 UTC moves an hour when the clocks change. So calsdk keeps two things on every timed event, the exact instant and the zone it was scheduled in.

## How does calsdk store timed events?

A timed `start` or `end` is a date-time plus the [IANA time zone](https://www.iana.org/time-zones) the event was scheduled in:

```ts
{ dateTime: '2026-11-03T10:00:00+05:30', timeZone: 'Asia/Kolkata' }
```

Events you read always have an offset in `dateTime`, so `new Date(event.start.dateTime)` is the exact instant. `timeZone` says how to show it and how a series repeats: a weekly 10:00 meeting in `Europe/Berlin` stays at 10:00 Berlin time when the clocks change.

When you write an event, you can leave the offset out. calsdk then reads the `dateTime` as the wall clock in `timeZone` and adds the right offset, daylight saving time included:

```ts
await createEvent({
  calendar,
  event: {
    title: 'Planning',
    start: { dateTime: '2026-03-30T09:00:00', timeZone: 'Europe/Berlin' }, // stored as +02:00
    end: { dateTime: '2026-03-30T10:00:00', timeZone: 'Europe/Berlin' },
  },
});
```

`timeZone` must be an IANA name, such as `America/New_York`. A Windows name, such as `Pacific Standard Time`, throws `InvalidArgumentError` with the IANA name to use instead. Outlook reports [Windows names](https://learn.microsoft.com/en-us/graph/api/resources/datetimetimezone), and calsdk turns them into IANA names when reading.

## How does calsdk store all-day events?

An all-day `start` or `end` is a date, with no time and no zone, because a holiday on the 12th is on the 12th wherever you are:

```ts
{ start: { date: '2026-11-12' }, end: { date: '2026-11-14' } }
```

The end date is exclusive: this event covers the 12th and the 13th, and a one-day event on the 12th ends on the 13th. That's the same rule as [iCalendar's `DTEND`](https://datatracker.ietf.org/doc/html/rfc5545#section-3.8.2.2), the [Google Calendar API's `end`](https://developers.google.com/workspace/calendar/api/v3/reference/events) and [Microsoft Graph's all-day events](https://learn.microsoft.com/en-us/graph/api/resources/event), which end at the next midnight.

An event cannot mix the two forms: `start` and `end` are both timed or both all-day. The [event model](/docs/concepts/events) shows them on a full event.

## Time windows

`timeMin` and `timeMax`, on `listEvents`, `getFreeBusy` and `findFreeTime`, take a `Date` or an ISO 8601 string. They're exact instants, not wall-clock times, so give strings an offset:

```ts
// Midnight to midnight in Berlin.
await listEvents({ calendar, timeMin: '2026-11-09T00:00:00+01:00', timeMax: '2026-11-10T00:00:00+01:00' });
```

A string without a time, such as `'2026-11-09'`, is midnight UTC. A date-time without an offset is read in the server's local zone, as JavaScript's `Date` does, which is rarely what you meant.

## Free time

Busy blocks and free slots are plain instants, `{ start, end }` in UTC. `findFreeTime` reads `workingHours` in the zone you give them, so "9 to 5 in Berlin" stays 9 to 5 across daylight saving changes. [Find free time](/docs/guides/free-time) walks through it.
