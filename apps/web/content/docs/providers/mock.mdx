The mock needs no credentials and makes no requests, so it's the quickest way to try calsdk and the right thing to put in your tests. It supports everything calsdk models except a free/busy endpoint, which also makes it the reference implementation for [provider authors](/docs/build-a-provider).

```npm
npm install @cal-sdk/core @cal-sdk/mock
```

```ts
import { listEvents } from '@cal-sdk/core';
import { mockCalendar } from '@cal-sdk/mock';

const calendar = mockCalendar({
  events: [
    {
      title: 'Standup',
      start: { dateTime: '2026-11-02T10:00:00+05:30', timeZone: 'Asia/Kolkata' },
      end: { dateTime: '2026-11-02T10:15:00+05:30', timeZone: 'Asia/Kolkata' },
      recurrence: ['RRULE:FREQ=WEEKLY;BYDAY=MO,WE,FR'],
    },
  ],
});

const { events } = await listEvents({
  calendar,
  timeMin: '2026-11-01T00:00:00Z',
  timeMax: '2026-12-01T00:00:00Z',
});

console.log(calendar.events); // the stored state
```

## How does the mock calendar behave?

The mock keeps ids predictable, `evt_1`, `evt_2` and so on, so your test assertions can name them. An occurrence is `<series id>_<UTC start>`, like [Google's](/docs/providers/google).

Seed events passed in `events` skip the checks `createEvent` runs, so give every `dateTime` an offset. `createConference: true` adds a placeholder link with `provider: 'other'`. Free/busy is computed from events by calsdk, with a `compatibility` [warning](/docs/concepts/warnings), as it is for any provider without an endpoint.

[Test your code](/docs/guides/testing) covers the settings and how to use the mock in tests.

## Which recurrence rules does the mock support?

The mock accepts one [RFC 5545](https://datatracker.ietf.org/doc/html/rfc5545#section-3.8.5) `RRULE` line plus any `EXDATE` lines. `RDATE` and `EXRULE` throw `UnsupportedFunctionalityError`. [Recurring events](/docs/guides/recurring-events) shows how to write and change a series.
